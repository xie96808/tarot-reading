# 烛下塔罗界面资源与动画优化设计文档

版本 1.0 · 2026 年 10 月 6 日  
对象：[线上网站](https://tarot.xieyw.top/)与本地项目  
用途：交给后续开发 AI 的设计约束、实现任务与验收依据。本次只交付设计文档，不修改业务代码或部署。

## 1 设计结论与使用方法

保留现有的暗色书房、米白牌背、RWS 牌面与克制的金色。网站已经有辨识度，问题不是缺少装饰，而是仪式被拆成了太多表单步骤，牌桌会随对白伸长，操作和说明反复出现，动画与文字也没有始终遵循同一个节拍。

本轮的主方向是：**一张稳定的牌桌，一条清楚的操作路径，牌先被看见，解释随后出现。**

“没有 AI 味”不等于故意打乱对齐。导航、表单和按钮仍应整齐可预测；自然感来自真实的视觉重心、具体的措辞、适量留白，以及每个动作都有明确来处和去处。不要用随机倾斜、满屏纸纹、额外粒子或更多诗句来弥补流程问题。

开发顺序：先读第 2 节确认基线，再完成第 3 节的阻断问题；按第 4—8 节完成布局、交互、动画和资源；最后按第 10—12 节测试、交付。文中的尺寸与动画时长是项目设计初值，不是已测得的性能或通用行业定律。

### 本轮明确不做的事

- 不换品牌，不改成紫色渐变、玻璃卡片、星空粒子或聊天机器人页面。
- 不重新生成 78 张牌面，不改变牌义与牌面对应关系。
- 不改变随机算法、牌序承诺、正逆位结果、分享编码和用户隐私默认。
- 不增加账号、登录、服务端 AI 对话或额外追踪平台。
- 不为了“高级感”引入 WebGL、3D 引擎、视频背景或大型动画依赖。
- 不把本地已有草稿或素材当作可覆盖的空白文件。

## 2 已检查范围与证据边界

### 2.1 实际体验

检查时间跨 2026 年 10 月 5—6 日。通过浏览器实际访问网站，而不是仅根据代码猜测：

- 桌面约 1265 × 712 的可见画面：首页 → 入席 → 不设问题 → 三张牌 → 推门 → 自动洗牌 → 切牌 → 发牌 → 逐张翻开 → 解读 → 结束。
- 手机视口 390 × 844：入席、问题、选阵、过手、自动洗牌、切牌、发牌、第一张翻开与跳过回应。
- 桌面该局为“命运之轮逆位、宝剑四正位、圣杯十逆位”；手机首张为“正义逆位”。这仅是复现观察，不是固定测试种子。
- 检查了本地状态机、牌面加载、洗牌、切牌、翻牌、暂停对白、阅读区、字体与静态资源。

**未完成的项目**：真机触摸长按、iOS Safari/Android 性能录制、帧时间统计、弱网与 CPU 限速、单张及凯尔特十字的线上完整流程。本文为这些项目规定了验收方法，但不把它们写成已通过，也不声称网站目前掉到某个帧率。

### 2.2 线上和本地不是可直接等同的版本

本地 HEAD 为 `4e03d86`。本地有用户既存的未跟踪文档与手部素材，保持原样。

线上手机页面实际引用了：

- `/table/felt-mat-oval.webp`
- `/hands/receive/hold.webp`

本地当前资源树没有这两个文件；本地 `TableScene` 仍以 CSS 绘制桌垫，`Card3D` 过手资源指向 `/hands/1.png`。因此下面的“代码定位”表示本地可核查入口，不等于线上部署的确切实现。正式开发前必须记录线上版本与实际发布来源；不要把本地旧组件直接覆盖到线上新素材方案上。

既有文档 [时间之河体验计划](/Users/xiexuan/codes/github_projects/tarot-reading/docs/time-river-experience-plan.md) 已提出减少问卷感、动作与话语一致等方向。本文继承这些方向，补入本轮线上观察、尺寸、事件时序和可执行验收；两份文档冲突时，以本文明确的“本轮决策”为准，其余保持兼容。

### 2.3 可复现的发现

| 编号 | 来源与现象 | 对体验的影响 | 对应设计 |
|---|---|---|---|
| O01 | 首页开始后，还有一整页“我准备好了”，再进入问题与选阵 | 用户已经表达开始意愿，却被重复确认 | 合并准备页，见 4.2 |
| O02 | 桌面问题页约 712px 高的可见区域内，示例按钮挤在底部，继续操作在下方；示例、主动作、返回使用相近的大框 | 主次不清，需要找下一步 | 示例降级，主操作固定在表单末端，见 4.2、5.2 |
| O03 | 三张牌要求先理解并选择“推门/过手”，否则“开始洗牌”禁用 | 动画偏好成为开始门槛 | 提供默认样式，设置渐进展开 |
| O04 | 翻牌区同时有牌面点击、“翻开”、外围“翻开过去”、上一位/下一位；进度也重复 | 同一动作多套入口，用户不清楚哪个是推荐路径 | 一个主要翻牌动作，已读牌位用于回看 |
| O05 | 推门首张停止在倾斜窄牌面，中间实色金条继续遮挡图案；下方同时出现大块浅色选择面板 | 牌与对白争夺注意力，“打开”像尚未完成 | 默认一次完整翻开；取消半翻强制答题 |
| O06 | 第二张已是“现在 · 宝剑四”，引导仍显示“第一张是过去” | 文字与当前牌位错误 | 由 positionId 生成文案，优先修复 |
| O07 | 跳过第一张回应后，第二张开头为“刚才你没有点” | 像操作日志，给跳过增加心理负担 | 不点评跳过；直接进入当前牌 |
| O08 | 点击翻牌/跳过后，焦点转到对白或解释标题，视口随之移动；牌桌还随面板增减高度 | 用户容易错过翻牌或失去空间位置 | 固定舞台、对白外置、焦点与滚动分离 |
| O09 | 手机过手首张停顿时，`innerWidth=390`，根节点与 body 的 `scrollWidth=400`；手部显示宽约 425px | 已确认横向溢出；具体责任元素仍需开发阶段定位 | 限定手部绘制层，不用全页隐藏溢出掩盖问题 |
| O10 | 同一手机状态，桌面背景显示框约 335 × 1237px，桌垫约 317 × 1179px；牌位按钮排成两行 | 桌面随对白被拉成长条，三张牌缺乏整体关系 | 舞台与文本分离，稳定牌位总览 |
| O11 | 过手大手掌占据牌面两侧；初次捕获画面手尚未出现，随后可见 | 手部抢占内容区；其迟到是否由下载/解码导致待测 | 动作前准备资源，手只为拿取服务，结束后撤手 |
| O12 | 推门流程翻牌瞬间，无障碍树出现“牌面载入中…” | 翻牌与牌面就绪存在时序风险；不等同于已测定可见闪白时长 | 为实际显示候选图建立 decode 就绪门 |
| O13 | 解读有“整阵线索、留给自己、今天先看到这里”，结束后再次完整显示解读与收束 | 完成感被重复总结削弱，保存/分享距离变长 | 保留一份结果正文，结束只改变状态与操作 |

未观察到大量 emoji 堆砌。现有的少量星形装饰不是首要问题，不应为了迎合“去 AI 味”而无依据地重做所有图形。

## 3 优先级与完成条件

### P0 先消除错位和不连续

1. 修复 O06 的牌位错文案，增加过去/现在分别断言。
2. 修复手机横向溢出与桌垫随长文变形；保持牌、标签、按钮互不遮挡。
3. 洗牌、切牌、发牌使用同一个稳定舞台；不因章节更新整块淡出、重新挂载或自动滚动。
4. 牌面完成解码再执行翻面；加载失败保留同一张牌的结果与重试入口。
5. 动画完成事件与交互解锁共用时间线；防连点、防旧回调推进新局、防隐藏标签页恢复后补播。

### P1 重建清晰的使用路径

合并开始前的准备步骤；整理按钮层级；对白和牌义外置；去掉强制半翻停顿；默认不自动转正逆位；结果页不重复输出同一解读；补齐键盘、读屏、减少动画与小屏规范。

### P2 精修素材与表现

字体拆分、桌垫质感与手部接触关系、接触阴影、可选过手增强版。P0/P1 未通过之前，不增加视频、光晕、镜头推进或新的拟人旁白。

## 4 页面与操作路径

### 4.1 首页

保留“给此刻，留一盏灯。”与右侧三张牌的非对称构图。正文只保留一句功能说明，例如“抽一张牌，或用三张牌看看眼前的处境。”首页的诗意只负责邀请，不承担每一步操作解释。

- 主按钮统一为“开始抽牌”。原“入席”可保留作章节小标题。
- 三种阅读方式保留名称，但先让人看到“单张 / 三张 / 凯尔特十字”，阅读时间作为辅助信息，不做等级、评分或推荐徽章堆叠。
- 首页选了牌阵，准备页直接预选；不重复要求确认同一选择。
- 三张牌的倾斜只用于首页展示。功能页牌位整齐稳定，避免人为随机错位。
- 手机首页允许小幅滚动，但标题、说明、主动作应在首屏，不让装饰牌压走主操作。

### 4.2 准备页

“我准备好了”独立步骤合并到准备页。主流程从首页开始到进入洗牌，除可选填写外，只需一次“开始洗牌”。

准备页按顺序排列：标题 → 可选问题 → 牌阵 → 主操作。问题初始显示约三行，标签“想问什么？（可留空）”；示例收进“看看提问示例”，不是两个同级大按钮。

牌阵使用一个单选组，默认三张。名称、张数、用途保持两行以内；“纳入逆位”默认值延续当前设置，并在“阅读设置”内解释。选择控件使用 radio/radiogroup 语义，而不是看起来像可以多选的 checkbox。

**动画模式决策**：新局默认“标准翻牌”，不要求理解推门/过手。阅读设置可切到“过手”；手素材未验收时不展示此选项。旧会话仍能恢复原 sceneId；旧推门会话恢复后也能继续，不因 UI 简化而丢失暂停答案。显示模式与讨论内容逐步解耦，不把视觉偏好变成另一套抽牌逻辑。

“这次不设问题”独立按钮可删除：空输入直接开始即可。输入的隐私说明在输入框附近保留一次；帮助与使用边界在页尾保留稳定入口，避免每次对白重复插入整块提示。若用户主动进入相关帮助场景，仍清楚显示原有完整信息。

### 4.3 洗牌与切牌

洗牌页直接可见牌堆和主按钮“洗牌”。点击播放一次完整洗牌再收齐，按钮即时改为“正在洗牌”。长按牌堆继续作为熟悉用户的可选控制方式，说明为“也可以按住牌堆，松开结束”。手机不显示“空格键”说明。

长按是补充，不是唯一方式。正常滚动页面不误触洗牌；pointercancel、失焦、切后台必须结束按住状态。键盘 Space 仅在洗牌按钮或牌堆获得焦点时接管，不在整个 window 上劫持空格；Enter 与点击等价。

收齐后，牌堆原地进入切牌。主操作“确认切牌”；“随机切牌”为次级文字按钮。滑块保留可精确操作的 label 与值；“上方 39 张 / 下方 39 张”只出现一次，不在桌上、滑块上、说明段同时重复。

“查看封存”改为“抽牌记录”折叠入口，详细记录保持完整。牌序承诺发生在何时由原算法决定，不为迎合文案改动提交时机。

### 4.4 发牌与逐张翻牌

当前“抽卡”是从既定牌序发牌，不是从 78 张牌中任意点击选取。本轮保留这一语义。无需另加一屏扇形 78 张选择，也不在每次点击翻开时重新抽取结果。

三张牌按左、中、右落到固定位置。发完后一句“先看第一张。”，主按钮“翻开第一张”。牌面本身也可点击，但与按钮触发同一个去重动作；不再在牌下面额外重复一套“翻开”按钮。

翻牌完成后显示“过去 · 命运之轮 · 逆位”这种明确标题，再出现当前牌的简短读法。主要前进动作变为“看第二张”；“返回第一张”等回看入口放在牌位导航，不重复“上一位 / 下一位”整排按钮。

三张牌保持从过去到现在到接下来依次打开。已打开牌可回看，未来未打开牌不提前泄露名字、alt 或牌义。进度只保留一处，例如“第 1 张，共 3 张”，半翻开始不等于完成翻开。

### 4.5 回应与阅读

对白在牌完整可见后出现。默认流程不要求先选一项、改一句话、再确认，才准看牌义。

- 当前牌：一条图像观察 + 一段读法；“说说你的想法”按需展开输入。
- 轻量回应可保留“有点像 / 不太贴近 / 先往下看”，但不强迫用户选择，不把它们推断为心理事实。
- “解读依据”默认折叠，保留来源透明性；它不是每张牌必须经过的一页。
- 单张：翻开 → 读法 → 可选记录，无三张牌的过去/现在语言。
- 凯尔特十字：桌面保留十字结构，手机显示小型位置地图与当前大牌。避免把十张牌都压成可点击的小邮票；各位置名称与序号源自现有 spread 数据。

### 4.6 结束与分享

阅读页只保留一份结果。用户点击“结束”后不再复制整篇阅读，也不输出一次按钮操作复盘。页面当前位置保留，显示短状态“这次阅读已结束”，提供“保存到此设备”“分享”“再抽一次”。

记录输入为可选，标题“记一句话”。保存私密文字、分享问题的开关延续当前默认不选中；分享前让用户看见实际会包含的内容。不用“收藏成功”代替本地保存失败的真实反馈。

## 5 布局与视觉规范

### 5.1 桌面和手机结构

桌面宽屏建议以 1120px 为内容最大宽度，主场景约 720—760px，阅读区约 300—340px，间隔 24px。只在容器确实容得下时使用双栏；中等屏宽采用上下布局，不硬塞侧栏。

```text
桌面阅读
烛下塔罗                         牌典  方法
三张牌 · 看过去、现在与接下来的方向       退出

┌────────── 稳定的牌桌 ──────────┐  当前牌位及牌名
│                               │  一条观察
│       过去    现在    接下来    │  简短读法
│       [牌]    [牌]     [牌]    │  解读依据 ▸
│                               │  说说你的想法 ▸
└───────────────────────────────┘  [看第二张]
             第 1 张，共 3 张

手机阅读
烛下塔罗                         更多
三张牌                         退出
┌──────── 稳定的牌桌 ────────┐
│    小型总览：过去 现在 接下来 │
│          [当前大牌]          │
└───────────────────────────┘
过去 · 牌名 · 正位或逆位
一条观察及当前读法
解读依据 ▸   说说你的想法 ▸
──────── 操作区 ─────────────
                    [看第二张]
```

这是结构示意，不是要把屏幕画成很多边框盒子。牌桌、正文和操作通过间距分组，浅色纸张只在完整阅读模式中出现一次，不在深色桌面里不断弹出浅色问卷。

手机以 390 × 844 为主要设计尺寸，同时适配 320px 宽。外边距 16px，极小屏可用 12px；标题栏约 56px。不要像当前布局一样把品牌与三个导航分成两层，再加大段章节留白。

洗牌/切牌/发牌舞台建议手机高 300—360px、桌面高 400—460px，短屏根据可用高度降低舞台而不是挤压文字。用户自主切到阅读状态时可以一次重新安排布局，但每条对白出现都不得改变舞台尺寸。手机当前牌宽约 144—168px；长文字位于舞台之外。

手机操作区使用正常文档流优先；确需 sticky 时只保留一个主按钮，增加底部安全区和等高占位，不覆盖内容。虚拟键盘弹出时保证输入框和完成动作可见，不把操作条钉在键盘背后。不要锁死 body 滚动。

### 5.2 控件与字体

| 元素 | 规格与行为 |
|---|---|
| 主按钮 | 每个当前任务区域最多一个；48px 高，适度金色填充配深色文字；明确 hover/pressed/focus/disabled 状态 |
| 次级按钮 | 透明底或文字链接，44px 以上触控高度；不与主按钮同等强调 |
| 退出 | 顶部稳定位置；有未完成记录时给现有确认机制，不做醒目危险色常驻按钮 |
| 页面标题 | 28—36px，行高约 1.3；手机 24—28px；保留现有文楷风格 |
| 操作与表单文字 | 16px，系统中文无衬线栈；不为“文艺”牺牲识别速度 |
| 阅读正文 | 17—18px，行高 1.75—1.85，可使用现有宋体；桌面行宽约 28—36 个汉字 |
| 辅助说明 | 14px，真实可读；不靠低到看不清的透明度做次级信息 |
| 图标 | 仅用于返回、展开、关闭等功能，采用统一细线 SVG；无装饰 emoji |
| 焦点 | 清楚的 2px 外框，键盘顺序与视觉顺序一致，不把每段静态说明都设为 Tab 停靠点 |

保留现有颜色基底：`#100e0c` 深背景、`#f4ecd5` 主文字/纸张、`#c4a35a` 金色强调。正文与辅助文字需要在实际背景叠层上测量对比度，不只比较 token。普通文字至少 4.5:1，大字至少 3:1；禁用状态不要拿来承载必要说明。依据：[WCAG 文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。

纹理只出现在材质上，强度以“不影响文字边缘”为准。全屏噪点、动态灯光、漂浮微粒都不是必需；默认去掉漂浮微粒和循环呼吸牌堆，静置页面应真正安静。

### 5.3 焦点与滚动

大页面切换可以把焦点移到新标题；舞台内部动作只更新状态，不滚回章节标题。对白出现时使用一次简短的 `aria-live="polite"` 状态通知，不立即把焦点从翻牌按钮夺走。

键盘触发后原按钮若将被移除，动画结束后把焦点移到新主动作，使用 `preventScroll`；仅当焦点目标完全不可见且非用户正在滚动时，执行一次最短距离滚动。长篇正文变化不整篇播报。

本地 `RitualApp` 的阶段滚动，以及 `PauseSheet/PauseMeaning` 的自动 focus 都需要一起处理；只删其中一个仍可能出现视口跳动。

## 6 文案与文字出现顺序

### 6.1 语言准则

首页允许一句有性格的邀请；过程尽量直说动作；牌义区允许意象，但把“画面是什么”和“可以怎样理解”分开。不要声称已经理解一个没写问题的用户，更不要把“跳过”解释为抗拒或沉默的深意。

每张牌最多一个开放式问题，不逐个点名画面物件让用户做选择题。“不太贴近”应改变后续讨论方式，而不是触发另一段同样的劝导。没有上下文时不补“沿着刚才那一步”。

| 现状 | 建议正文 |
|---|---|
| 入席，开始一次抽牌 | 开始抽牌 |
| 此刻，什么事占着你的心？ | 今天想看看什么？ |
| 把问题放轻，把牌打散。 | 洗牌 |
| 正在封存 | 正在收齐牌；技术承诺状态仍在记录中准确显示 |
| 把手伸进牌的中间，为这一局落一个切口。 | 选一个切牌位置 |
| 让牌落在桌上 | 确认切牌 |
| 第一张是过去，用于每个暂停 | 第一张：先看看过去。／第二张：看看现在。 |
| 刚才你没有点。 | 删除该句；直接介绍当前牌 |
| 你要先把剑尖转到哪一边？ | 这张牌让你想到什么？（可选，且不宣称用户移动了牌中物件） |
| 牌已经说完它的部分。接下来，轮到你慢慢生活。 | 这次阅读已结束。 |

不要全站机械替换词语。逐个页面判断一句话是否让人知道发生了什么、下一步是什么；两者都不承担就删掉。整阵解读只留一段真正连接各牌的内容，不额外总结按钮、牌数与操作顺序。

### 6.2 文字过渡

- 按钮状态更新：点击后立即反馈，目标 100ms 内可见，不等整场动画结束才改变文案。
- 短提示切换：先淡出 80ms，再淡入 120ms；两段文字占同一预留区域，避免垂直跳动。
- 牌名：牌面落稳后出现，淡入 120—160ms。
- 牌义：紧接牌名出现，160—200ms 淡入；不逐字打字、不按句子强制等待。
- 同时只让一个主要注意对象变化。翻牌进行中不展开问卷、不改变舞台高度、不自动滚动。
- 预留提示区约两行；长文正常排版，禁止用固定高度裁掉正文。用户扩大字体时优先自然增高。

## 7 动画设计与准确性

### 7.1 统一空间

从洗牌到最后一张牌翻开，使用同一个稳定的舞台容器。木纹、灯光方向、牌背尺寸与透视统一；牌从真实牌堆位置出发，落在真实牌位位置，不从舞台上方一个新出现的小牌堆“传送”出来。

卡牌变换分层：布局/飞行层负责 translate，翻面层负责 rotateY，正逆位观看层负责 rotateZ，阴影单独一层。不要让 CSS animation 与 transition 同时写同一个节点的 transform。

所有视觉参数来自一个 motion token 来源。优先 CSS transform/opacity 或轻量 WAAPI；必要测量在动作开始前批量读布局，下一阶段批量写样式，不在每帧交替测量和更新 React state。transform/opacity 更容易避免布局与重绘开销，但仍须用实际 trace 检查合成和帧表现。依据：[浏览器动画性能指南](https://web.dev/articles/animations-guide)。

### 7.2 时间线初值

| 动作 | 建议时间 | 明确的起止画面与完成条件 |
|---|---|---|
| 控件按下反馈 | 80—120ms | 边框/背景响应即可，缩放最多 0.98，不让按钮位置跳动 |
| 自动洗牌 | 总计约 1600ms | 0—160 拿稳；160—1100 两叠交错；1100—1500 收齐；1500—1600 落稳 |
| 长按洗牌循环 | 约 1400ms/循环 | 循环首尾的姿态与速度连续，不每轮重闪手图 |
| 松开后收齐 | 240—360ms | 从松开那一帧的真实姿态归拢，不跳回固定关键帧 0 |
| 切牌合拢 | 440—520ms | 上叠按算法实际移到牌底；抬起、让位、叠合，次序清楚 |
| 发单张 | 飞行 480ms，起始间隔 160ms | 三张最后一张在 800ms 落稳，再留 80ms；十张在 1920ms 落稳，加余量共约 2000ms |
| 标准翻牌 | 约 480ms | 轻抬最多 4px，rotateY 0→180；约 80ms  settle，完整 560ms 内结束 |
| 过手增强翻牌 | 约 720—880ms | 手进场拿稳、牌翻开、放回、撤手；无答题暂停 |
| 手动查看逆位方向 | 220—280ms | 只改变观看角度，不改变牌的 orientation 数据 |
| 手机总览到当前牌 | 220—280ms | 同一张牌的几何位置连续过渡，而非三张全部消失重建一张 |

缓动初值：普通位移 `cubic-bezier(.22,.61,.36,1)`；翻面 `cubic-bezier(.4,0,.2,1)`；循环使用首尾速度连续的分段曲线。牌是纸，不是果冻：落桌不大幅弹跳，倾斜不超过动作所需，禁止 spring 多次回弹。

“约 1600ms 自动洗牌”已经包含收齐，不再外加当前至少 1900ms 的提交等待。手动长按由用户决定时长，松开后也无需再重播一整轮自动洗牌。只有实际算法未完成时才继续显示真实等待状态。

### 7.3 洗牌

使用 8—12 个可见牌片就足以表达厚度，不渲染 78 个独立运动对象。两叠共享轨迹，可见上层牌微错开。静止阴影常驻；动效只改变阴影图层的 opacity/transform，不给每张牌增加逐帧 blur。

本地当前 holding 的 riffle 和 committing 的 seal 是两套 keyframes，seal 从固定初态开始，用户在循环中任意时刻松手可能跳变。改为读取/保存当前动画进度并平滑归拢，或设计可安全退出的循环段；两者择一，不用透明淡出遮掩跳变。

动画只是既定抽牌过程的呈现。长按时长不应被文案包装为“更准”；如现有随机输入采样参与洗牌，保持既有算法合同与测试，不为视觉可重复而改生产随机性。

### 7.4 切牌和发牌

切牌起始牌堆中心与洗牌结束中心一致。两叠离开原点后保留可追踪的身份；显示张数与实际 cutIndex 一致，极值 1/77 仍不穿模。

发牌前测量真实源牌堆与目的牌位。飞行期间不显示牌面；各牌落稳后再允许对应翻牌。最后一张完成决定“发牌结束”，不要只用一个最大 cap 掐断尾段。

当前手机发牌总览与逐张阅读使用不同布局。新实现先保持缩略总览，再让当前牌进入稳定大牌区域；回看也沿相同方向移动，不每次重新播放发牌。

### 7.5 翻牌与逆位

本轮默认一次完整翻牌，翻完再邀请回应。删除“126°停住、等待回答后才完整打开”的必经环节。推门的记忆点如要保留，只在开始 100—140ms 内以很细的边缘光表现，不在牌面正中留下 12px 实色条。

**逆位默认保持抽到的方向**，旁边明确“逆位”；“转正看图”是用户可选操作，转正后仍标“逆位”。不再自动多转半圈，让用户误以为逆位变成正位。历史会话中的 orientation、解读和分享结果保持原值。

正反面同时存在且使用 backface-visibility；检查 Safari 侧边闪烁、前后面镜像和父层 flattening。旋转角度与读屏文本来自同一份状态。尚未揭示的牌不因为提前解码而出现在无障碍树里。

### 7.6 过手素材的门槛

手应有拿取任务，而不是从透明度 0 放大到 1 的巨型背景照片。手和牌需要共享锚点：接触期间相对位置固定，牌放下后手独立撤走。

若只是整张静态手图平移，使用张开的托牌姿势，不伪装复杂穿插的手指动作。如果表现抓握，需分离后掌、前指、卡牌三个遮挡层，或提供同一镜头、同一人物的连续手势素材。严禁在不匹配的手照片之间硬切。

当前手机手部约 425px 宽，大于 390px 视口。重新按舞台内的接触区域定位，而不是全局用卡牌宽度 250% 放大；手腕在舞台边缘自然出画，裁切发生在装饰绘制层，卡牌、按钮和焦点框不跟着被裁掉。

手部任何一项不达标：指节结构、光向、透明边缘、锚点、遮挡关系或资源准备，首版使用无手的标准翻牌。宁可少一个动作，也不要保留看起来像漂浮贴图的手。

### 7.7 统一状态与异常处理

建议把业务状态与视觉状态分开管理。沿用现有 reducer 处理牌序和结果，新增或整理视觉协调层；不为了动画重写所有业务。

```text
业务：准备 → 洗牌已提交 → 切牌已确认 → 已有 draws → 阅读 → 完成
视觉：idle → shuffling → gathering → cutting → dealing → ready
                                          ready → preparingFace
                                                → revealing
                                                → readable
```

事件合约：

- 每次动作带 sessionId、operationId、positionId（适用时）；旧局回调直接忽略。
- `FACE_READY` 表示实际候选图已解码，不只是 manifest 已获取。
- `REVEAL_FINISHED` 才更新“已翻开”计数并展示牌义；业务结果早已确定，不重新抽牌。
- 动画完成、取消、减少动画、标签页隐藏都有明确终点路径。超时兜底只用于收敛到合法终态，不生成新结果。
- 同一位置重复点击仅产生一次动作；整个舞台不必被一个长时间全局锁禁用，保留退出和帮助。
- 切后台时取消持有手势，暂停装饰；有限动作可收敛到已承诺结果的终态。返回后显示正确画面，不连续补播一串动画。
- 翻牌中调整视口：取消当前视觉运动并贴合当前合法布局，保留同一结果；不重新发牌。开发时可选择稳定重定位策略，但需测试。

### 8.3 加载与解码

1. 首页只加载首页用到的资源，先保证标题、主操作和牌背；不抓取 78 张牌。
2. 用户进入准备页后准备桌面与必要牌背。手部只有选择过手时才准备，失败不妨碍标准翻牌。
3. draws 确定后，提前加载本局对应牌面；三张可并行，十张优先当前及下一张，其余使用低并发队列。
4. 预载和显示使用相同的 srcset/sizes 计算规则与视口宽度。当前代码预载使用 170/130px，而逐张组件声明 `sizes="220px"`，存在命中不同候选资源的风险，应统一。
5. 对实际候选图等待 `decode()`；处理 rejection、src 候选变化和失效会话。单纯 onLoad、设置 src 或 fetch manifest 不等于动画用图已准备。
6. 加载超过 150—200ms 才显示轻量状态“正在准备牌面”；牌背留在原位。超过约 8s 提供重试/退出，结果保持不变，不重新抽取，也不无限等待。
7. 牌面成功后再翻；失败时在原尺寸卡位给“牌面加载失败，重试”，仍可在明确提示后查看该牌的文字信息。

`decode()` 的作用是等待图像解码完成，适合把资源准备从可见翻转中分离；并非它本身保证所有设备无卡顿。依据：[MDN 图像解码](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode)。

图片显式声明尺寸/比例；正文图片不要默认 `object-fit:cover` 裁切图案。缩略图可以缩放，但不得剪掉牌名、数字或牌边。内容哈希资源可使用长期不可变缓存，manifest 与 HTML 需可更新；不要给无版本路径直接永久缓存。

### 8.4 字体

控制文字使用系统字体；文楷用于标题，宋体用于阅读长文。不要全站为同一段文字同时下载几套完整中文字体。

先抓网络瀑布确认实际 woff2 请求，再制作 unicode-range 分片或基于确切页面固定字集的子集。用户输入保留系统字体 fallback，避免只覆盖页面文案导致用户姓名和问题缺字。标题字形切换应尽量匹配 fallback 字面与行高，避免按钮和标题换行。

### 8.5 视频和音效的取舍

**首版不引入视频。** 可交互、随机牌面、可取消的动作适合 DOM/CSS/WAAPI；预渲染视频难以精确响应松手、切牌位置与具体抽牌结果，也容易在结尾切回实时画面时跳帧。

若未来只为背景气氛加入短片：必须有同构 poster、暂停能力、移动端与减少动画下的静态版本；背景片不得承担真实翻牌。导出 MP4 与 WebM 可兼容版本，约 3—5 秒、首尾闭合、无声、默认延迟加载；首版媒体流量预算不因它被挤占。需在首次播放、循环接点、切后台恢复三个位置检查黑帧与解码停顿。

音效同样为可选，默认关闭，不自动播放环境音乐。只有用户主动开启后，洗、切、落牌各用极短克制声音；音效跟随已发生的动作，不用音频结束事件控制结果推进。

## 10 性能目标与验证方法

### 10.1 发布门槛

| 指标 | 目标 | 测量注意事项 |
|---|---|---|
| 首次 LCP | 真实用户移动/桌面分别 p75 ≤ 2.5s | 无真实样本时标“待观察”；实验室结果不能冒充线上 p75 |
| INP | 同上 p75 ≤ 200ms | 包含实际洗牌/翻牌输入，不用 Lighthouse 加载分数代替 |
| CLS | 同上 p75 ≤ 0.1；实验室目标 ≤ 0.05 | 用户输入附近的位移可能被指标排除，所以额外检查舞台位置跳动 |
| 动作反馈 | 正常设备按下到可见反馈 ≤ 100ms | 和动作完成时长分开，洗牌 1600ms 不等于响应慢 |
| 60Hz 目标设备动画 | 至少 95% 有效帧间隔 ≤ 20ms；>33.3ms 的间隔占比 < 1% | 项目内部预算；逐段报告，不用全程静止帧稀释 |
| 动画卡住 | 核心运动中无非预期 >100ms 的停顿 | 区分真实网络等待、录制开销、后台标签页 |
| 横向溢出 | `scrollWidth ≤ clientWidth + 1px` | 320/360/390/430px 与文字缩放状态均检查 |
| 结果一致性 | 同 seed/输入的 cardId、orientation、cutIndex、分享解码完全不变 | 减少动画、标准/过手与异常恢复都适用 |

LCP/INP/CLS 门槛来源：[Web Vitals](https://web.dev/articles/vitals)。其余帧率、流量、操作时长指标是本项目验收预算。高刷屏按实际刷新周期分析，别把 60Hz 的 20ms 预算当成 120Hz 满帧标准。

### 10.2 首次访问资源预算

以新会话、冷缓存、移动端为基准，观察到首次可操作为止：

- 首页关键图片合计目标 ≤ 180KB；首屏字体目标 ≤ 200KB。
- 首页压缩传输总量目标 ≤ 800KB；阅读路由新增 JS 目标 ≤ 120KB gzip，包含任何新增动画依赖。
- 已知的本局三张牌面加载目标合计 ≤ 350KB；桌面纹理与可选手势按需，不同时下载所有姿势。
- 预算超出时先提供资源瀑布与必要性解释；不要靠降低牌面到模糊来达标。

这些是新方案目标，不是当前线上统计。若框架基础包使目标不现实，先列出现状、差值和可削减项，经评审调整预算，禁止直接写“全部通过”。

### 10.3 录制协议

在生产构建上测试，不以 dev 模式结果作为性能结论。固定同一 seed/牌阵、视口、浏览器版本、系统、电源条件、网络和缓存状态。seed 注入仅用于测试环境，不公开到生产用户控制中。

分别记录：首页冷启动、自动洗牌、长按随机时刻松开、切牌极值、三张发牌、十张发牌、正位翻牌、逆位翻牌、过手、减少动画。每段至少 5 次，保留每次结果并报告中位/最差；不从 5 次样本推断真实用户 p75。

诊断场景可用 4× CPU 限速、下行 1.6Mbps/上行 750Kbps/RTT 150ms；这是可重复压力设置，不是中低端真机的替代。至少补一台近三年中端 Android、一台 iPhone Safari 的实机测试。

DevTools Performance 记录屏幕、主线程、Layout/Paint、长任务与合成帧；rAF 采样只能作辅助手段，不直接代表 GPU 实际呈现帧。明确 0ms、25%、50%、75%、完成点的截图或逐帧样片，检查跳变、闪白、穿模与手部接触。单独记录测量工具开销。

每次报告应含：构建 SHA、设备/浏览器、视口/DPR、测试输入、缓存/限速、动作起止、帧间隔分布、长任务、布局跳变、失败资源和原始 trace/录屏路径。问题与用户留笺不进入性能日志。

### 11.2 关键验收用例

1. **快速进入**：首页选三张，准备页不写问题，点一次“开始洗牌”即可开始；不存在必须选动画风格的门槛。
2. **牌位准确**：打开第二张时引导、标题、进度均为现在；第三张为接下来；单张不出现过去/现在措辞。
3. **松手连续**：在洗牌循环 10%、40%、70%、95% 位置松手，第一帧归拢与上一帧的位置、角度连续；无牌堆闪回中央。
4. **切牌准确**：cutIndex 为 1、39、77 时，视觉上下叠与实际移动的牌段一致；确认连点仍仅切一次。
5. **发牌同源**：录制中每张从同一个真实源牌堆出发，最后一张落稳前翻牌动作不触发；手机转换保留同一张牌身份。
6. **解码门**：延迟当前牌面请求，牌背保持完整；资源就绪再翻。失败重试后仍为同 cardId/方向，没有抽新牌。
7. **稳定阅读**：对白从短句换成长文、跳过回应或展开依据，牌桌高度/位置不变；当前牌不被自动滚出可视区域。
8. **逆位一致**：逆位首次可见保持倒向，文字标逆位；点击“转正看图”后解读与分享仍是逆位。
9. **触摸边界**：手掌和阴影不扩大文档宽度；滑动正文不洗牌，长按取消后没有卡死或持续动画。
10. **辅助功能**：Tab/Enter/Space 可完成流程；一次揭示只播报一次新牌摘要；隐藏牌的名称不提前出现；所有必要控制有可见焦点。
11. **减少动画**：无循环、3D 翻转、长距离移动和延迟锁；功能、结果与普通模式完全一致；帮助、退出始终可用。
12. **恢复**：背景停留后返回不补播；重载后保留原牌与已完成状态；旧推门/过手会话仍能结束。
13. **完成与保存**：阅读正文不重复；不保存可直接结束；保存失败真实提示；分享不默认包含问题/留笺。
14. **回归**：旧分享链接可解码；历史、牌典、方法、隐私入口可用；不因 UI 重构破坏现有测试保护的业务事实。

### 11.3 对“符合习惯”的小规模验证

至少邀请 5 位未用过网站的人，包含手机用户，任务为“不写问题完成一次三张抽牌，再找回第二张，并找到保存入口”。不口头告诉他们按钮在哪里。

初轮目标：至少 4/5 独立完成主流程；没有因误触退出或找不到下一步而中断；用户能区分“翻牌”和“改变抽牌结果”；结束后知道保存是否发生。这是形成性测试，不是对所有用户的统计保证。

记录犹豫、重复点击、滚动寻找和错误理解；不要只问“好不好看”。若某按钮仍需解释，先改流程或标签，再考虑增加提示文案。
